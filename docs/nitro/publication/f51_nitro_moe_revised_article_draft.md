# F51 Nitro-MoE: A Reproducible Measurement Note on GPT-OSS 120B MXFP4 Inference on a 16 GB Consumer GPU

Author: Marco Barreto, Fuch F51 Labs

Status: internal scientific draft, not submission-ready.

## Abstract

This note reports a local measurement study of GPT-OSS 120B MXFP4 inference on a consumer RTX 5060 Ti 16 GB system using a patched llama.cpp/F51 runtime. The archived run identifies the model geometry, expert tensor size, GPU memory buffers, token throughput, F51 cache hit-rate checkpoints, and a prompt-cache/SWA checkpoint correction. The current evidence supports a narrow claim: GPT-OSS 120B MXFP4 can be loaded and served locally with partial MoE CPU/GPU placement, but the measured archived generation speed is 3.22 tok/s over 33 generated tokens, not the larger Qwen headline numbers from earlier notes. Those larger numbers require fresh raw logs before journal submission.

## System And Model

The local measurement machine was an Intel Core i7-12700K system with 12 CPU cores, 20 hardware threads, 63.72 GiB RAM, and one NVIDIA GeForce RTX 5060 Ti with 16,310-16,311 MiB VRAM. The active driver reported by `nvidia-smi` was 595.97.

The measured model was GPT-OSS 120B MXFP4. The llama.cpp loader reported a 59.02 GiB model file at 4.34 BPW, 36 transformer layers, 128 experts per MoE layer, 4 selected experts per token, embedding width 2880, expert feed-forward length 2880, and training context length 131,072.

## Expert Tensor Accounting

The F51 diagnostic trace reported three MXFP4 expert tensor strides of 4,406,400 bytes each for gate, up, and down expert tensors. Therefore:

```text
expert_bytes = 4,406,400 + 4,406,400 + 4,406,400
             = 13,219,200 bytes
             = 12.61 MiB

full_expert_layer = 128 * 13,219,200
                  = 1,692,057,600 bytes
                  = 1.576 GiB

all_expert_tensors = 36 * 128 * 13,219,200
                   = 60,914,073,600 bytes
                   = 56.73 GiB
```

This accounting explains why full expert residency is not plausible on a 16 GB card and why partial residency or CPU-MoE placement is required.

## Archived Local Runtime Result

The archived MXFP4 run reported:

| Metric | Value |
| --- | ---: |
| CUDA model buffer | 1607.61 MiB |
| CUDA KV buffers | 144.00 MiB + 36.00 MiB |
| CUDA compute buffer | 609.15 MiB |
| Prompt speed | 4.22 tok/s over 68 tokens |
| Generation speed | 3.22 tok/s over 33 tokens |
| F51 hit-rate checkpoint range | 67.9% to 87.6% from token 50 to token 600 |

The SWA checkpoint patch should be treated as a correctness fix, not a performance result. The archived evidence says it avoided `wrong sequence id` and forced prompt re-processing in a four-request external validation, but it is not yet a controlled throughput benchmark.

## Claims Not Yet Supported By Current Raw Logs

Earlier drafts claimed Qwen 80B-A3B throughput values of 8.4 tok/s GPU-all, 17.2 tok/s CPU-only, 38.7 tok/s Nitro, and roughly 39-43 tok/s at 256K context. Those numbers may be real, but they are not publication-grade in this repo right now because the raw benchmark logs and repeated-run protocol are missing.

The same applies to the microbenchmark numbers 31 microseconds for GPU-resident expert execution, 164 microseconds for CPU execution, 695 microseconds for PCIe streaming, and +0.0 to +0.8 percentage points for speculative prefetch. These are useful internal hypotheses until the raw output of the benchmark programs is archived.

## Contribution After Calibration

The defensible contribution is a measurement and reproducibility artifact:

1. A concrete tensor-accounting method for estimating MoE expert residency pressure from GGUF/llama.cpp diagnostics.
2. A local GPT-OSS 120B MXFP4 serving configuration for a 16 GB consumer GPU.
3. A prompt-cache/SWA checkpoint fix for sequence-id retargeting in llama.cpp server slots.
4. A benchmark plan for separating CPU-only, GPU-all, CPU-MoE, and partial GPU-resident MoE modes.
